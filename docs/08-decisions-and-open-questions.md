# 架构决策与实施参数

更新日期：2026-11-01。版本：10 万并发目标架构。需求、核心技术与架构基线按下文固定，配置数值和厂商保证在实施验收中落定。

## 已确认需求与核心技术

| 事项 | 固定决定 |
| --- | --- |
| 产品 | 对外多租户 SaaS，企业与普通用户 |
| 容量目标 | 100,000 并发；独立文本边界、媒体在途边界、合计十万的混合场景 |
| 正确性底线 | 精确金额、不超授权、不重复收费、不错误解冻，未知事实不冒充精确账 |
| 任务范围 | 文本非流式/SSE、图片异步、视频异步均纳入目标 |
| 管理后台 | React + TypeScript + Vite |
| Client | Next.js + TypeScript，公开页面与用户/企业门户 |
| 业务后端 | TypeScript + Hono |
| LLM Gateway | Go，包含持久额度执行与媒体任务 Worker |
| 用户管理 | 中央业务系统管理，Gateway 只消费必要执行投影 |

## 架构实现规则

| 事项 | 实现规则 | 必须满足的约束 |
| --- | --- | --- |
| 实时准入 | Go 执行分片在中央已委托额度内持久化预占/启动 | 本地事务与同步确认延迟，不能纯缓存放行 |
| 资金权威 | 中央钱包/来源/预算分配/总账由 Billing 写，请求预占由运行时写 | 两层守恒、回执在途与安全回收 |
| 最终计价 | Billing 唯一最终收费实现；冻结价格/计量/舍入版本 | 上界与最终费用一致性、真实用量可核实 |
| 额度分配 | 按持久分片、多子池与完整硬预算范围授权 | 闲置额度占用、补充风暴、源追踪与关闭墓碑 |
| 可靠协作 | PostgreSQL Outbox/Inbox + Kafka + 幂等清算回执 | 不能用消息 Exactly-once 标签替代资金唯一键 |
| 生产数据库 | 独立中央 HA PostgreSQL + 按 Cell 的 HA runtime_db 分片 | 同步复制、旧主隔离、资源与恢复水位 |
| 权限撤销 | REVOKING、分片持久确认屏障、再 REVOKED | 失联分片下撤销可能保持处理中 |
| 任务处理 | 图片/视频持久受理、上界占用、有界调度、回调/轮询与取消核对 | 长任务占款、厂商状态/费用差异 |
| 商业模型 | 单结算币种、预充值按量与协议价 | 渠道、退款资格、失败收费规则仍需明确 |
| 部署范围 | 单区域多可用区，执行 Cell 水平扩展 | 跨区域灾备和双活另外设计，不复制整钱包 |

完整规范见 [高并发架构](<AI Token SaaS 10万并发架构设计方案.md>)、[数据库](03-database-design.md)、[账务](04-billing-and-ledger.md)、[接口](05-api-contracts.md) 与 [技术选型](<AI Token SaaS 最终技术选型方案.md>)。这里固定的是目标方案，不是已运行的容量结果。

## 实施前仍需固定的参数

| 事项 | 必须确定的内容 | 影响 |
| --- | --- | --- |
| 吞吐与负载 | 持续/峰值新请求 QPS、最大单企业 QPS、文本时长/输出、图片视频比例与大小 | Cell/副本/数据库/队列数量，不再询问是否需要十万并发 |
| 延迟与积压 | 准入和首 Token P99、清算/回执延迟、任务排队截止及回调洪峰 | 超时、容量余量、背压与额度水位 |
| 币种与计价 | 最小收费、业务舍入阶段与模式、视频/图片与 Token 指标映射；存储精度固定 NUMERIC(30,12) | 黄金样例、上界 E 与最终 C |
| 厂商与协议 | 各类任务适配器、上游幂等/查询/取消/用量保证、采购并发与额度 | 哪些结果可自动恢复，何时必须核对 |
| 支付与退款 | 渠道、可退来源、赠送与过期、手续费、消费退款是否回补原预算 | 账户来源和资金回收规则 |
| 失败收费条款 | 部分交付、取消已执行、文件保存失败、未知用量与超上界差额 | 客户费用、平台采购与损失分别入账 |
| 额度策略 | 子池范围、低/目标水位、每租户闲置上限、来源选择、窗口截止 | 补充频率、资金利用率与热点分散 |
| 可用性与灾备 | 故障域、同步确认配置、安全提升条件、RTO/RPO 与跨区域策略 | 已确认资金状态的保护和不可用时行为 |
| 认证与版本 | Better Auth 会话接入验证、SSO 采购要求、依赖和容器兼容版本 | 会话接入与供应链锁定，不重选核心四栈 |

缺少这些数值不把资金约束降级成最终一致的内存余额。无法确认额度、身份有效性或持久化时停止新增消费；合法历史清算与资金核对继续处理。

## 已固定的业务处理原则

- 相同业务意图保持原 request/task、原 home_shard；没有业务幂等键的重复调用分别计量。
- 已启动或提交未知不按 TTL 解冻；明确未发送的取消与启动原子竞争。
- 消费退款追加更正，原收费和子池 X 不改；充值款退款先回收可用委托资金。
- 调低预算不得突破已消费与未结清分配，可先停止新准入并回收未用额度。
- 价格与预算窗口按准入快照归属，旧窗口任务晚完成仍按原引用处理。
- 费用超过授权或无法核实用量时保留差异和证据，授权外不自动扣款。
